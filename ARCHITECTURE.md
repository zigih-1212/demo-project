# Архитектура и инженерные решения

Документ описывает, почему в демо-проекте выбраны именно такие технологии и как
они соотносятся с требованиями вакансии Fullstack Developer (Middle).

## 1. Контекст

Требования вакансии:

- проектирование архитектуры продукта, выбор БД, брокеров сообщений, стратегий кэширования;
- оптимизация запросов к API и производительность;
- организация непрерывного CI/CD;
- мониторинг и логи (Grafana + Prometheus);
- Docker, Kubernetes;
- очереди (Celery, Airflow), PostgreSQL;
- аудит наработок ИИ-агента и план рефакторинга;
- Python.

## 2. Два исполнения одной архитектуры

Проект реализован в двух исполнениях, потому что требования вакансии описывают
классический стек (Python/PostgreSQL/Celery/K8s), а для публичного демо нужен
запуск без единой VM.

| Слой | `backend/` (эталон) | `worker/` (демо на edge) |
|---|---|---|
| Runtime | Python 3.12, FastAPI, Uvicorn | TypeScript, Hono, Cloudflare Workers |
| БД | PostgreSQL 16 + asyncpg + SQLAlchemy 2.0 | D1 (SQLite) + raw SQL |
| Кэш | Redis (TTL + LRU) | Workers KV (TTL) |
| Очереди | Celery + Redis broker, Beat | Cloudflare Queues (producer/consumer) |
| Аутентификация | JWT + PBKDF2 (bcrypt) | JWT + Web Crypto API |
| Метрики | prometheus-client → Prometheus → Grafana | свой exposition-формат → Prometheus/Grafana |
| K8s | Deployment/Service/HPA/PDB/Ingress | не применимо (edge) |
| CI/CD | GitHub Actions: lint → tests → image → deploy | GitHub Actions: typecheck → tests → deploy |
| Тесты | pytest + asyncio + httpx (4 теста) | vitest: 24 unit + 24 integration (Miniflare D1+KV) + 9 frontend (RTL) |

Логика сервисного слоя, схема данных, контракты API и формат метрик — одинаковые.
Различается только транспорт и хранилище, что и позволяет держать один API-контракт
для фронтенда в обоих случаях.

## 3. Решения

### ADR-001. Основное хранилище — PostgreSQL

**Контекст.** Нужна транзакционная целостность, индексы, агрегатные запросы,
аудит изменений.

**Решение.** PostgreSQL 16, доступ через asyncpg + SQLAlchemy 2.0 (async).
Модели: `users`, `tasks`, `activity` с ForeignKey-связями. В worker-варианте —
D1 (SQLite) с теми же индексами и CHECK-констрейнтами.

**Почему не NoSQL.** Домен задач реляционный: статусы, приоритеты, исполнители,
срезы по датам. Реляционная модель даёт индексы и `COUNT/GROUP BY` без агрегатов
на стороне приложения.

**Индексы.** `ix_tasks_status_created_at`, `ix_tasks_priority`, `ix_tasks_assignee`,
`ix_tasks_created_by`, `ix_tasks_due_date` — покрывают основные паттерны
фильтрации из UI.

**Миграции.** Alembic (ревизия `0001_initial`) для версионирования схемы.

### ADR-002. Кэш — Redis со стратегией read-through и инвалидацией по записи

**Контекст.** Список задач и агрегаты читаются часто и меняются редко.

**Решение.** Read-through кэш: промах → БД → запись в кэш с TTL 60 с.
Запись (create/update/delete) инвалидирует ключи `tasks:list:*` через `SCAN`+`DEL`.

**Почему не write-through.** При write-through операция записи затрагивает два
хранилища и при падении кэша теряет согласованность. Read-through + инвалидация
проще дебажить, а потеря кэша безопасна.

**Ограничение.** `expirationTtl` в Cloudflare KV — минимум 60 секунд, поэтому
TTL 30 с приводил к ошибке; выбран 60 с.

**Первая реализация инвалидации делала `list(prefix) -> delete` по каждому ключу.**
На live-стенде обнаружилось, что после удаления задачи `total` в ответе
оставался прежним: **KV в Cloudflare eventually consistent** — только что
записанный ключ ещё не виден в листинге, поэтому инвалидация его не
затрагивала и наружу отдавались устаревшие данные.

**Решение.** Отказ от удаления ключей в пользу версионирования namespace:
счётчик версий лежит в одном ключе, инвалидация — это `+1` к счётчику, и все
старые записи становятся недостижимыми мгновенно, без ожидания распространения
индекса. Старые ключи истекают по TTL. Побочный эффект — нет листинга ключей и
нет O(N) операций при инвалидации.

Известное ограничение: две параллельные инвалидации могут прочитать одно и то же
значение счётчика, и одна потеряется. Для компенсации ключ версии пишется с
TTL, а источником истины остаётся БД. Для продакшена при параллельных
писателях счётчик выносится в Durable Object.

### ADR-003. Очереди — Celery (worker) / Cloudflare Queues (edge)

**Контекст.** Требования упоминают Celery и Airflow. Airflow — планировщик
ETL-процессов, а задачи здесь — фоновая обработка запросов, а не data pipeline.

**Решение.** Celery + Redis broker + Beat для расписания (переиндексация, выгрузка,
ежечасный аудит). В worker-варианте — Cloudflare Queues с тем же контрактом задачи
(`type`, `taskId`, `requestedAt`).

**Идемпотентность.** Consumer идемпотентен: повторная доставка не должна
дублировать эффект. Для этого задачи идемпотентны по идентификатору.

### ADR-004. Мониторинг — Prometheus + Grafana, метрики вручную

**Контекст.** Нужно отслеживать RPS, ошибки, латентность, попадания в кэш.

**Решение.** `/metrics` отдаёт текст в формате Prometheus exposition.
Реализация — собственный минимальный регистр (`worker/src/lib/metrics.ts`):
счётчики, gauge, гистограмма с бакетами. В Python-варианте — `prometheus-client`.

**Почему не Prometheus-клиент в edge.** Он рассчитан на CPython и тянет
multiprocessing-регистр; в Workers это лишний вес. Формат вывода тот же,
с Grafana совместимость полная.

**Алерты.** `infra/prometheus/rules/slo.yml`: доля 5xx > 5%, p95 > 1 s, отсутствие
трафика 30 мин.

### ADR-005. Аутентификация и autorизация

**Контекст.** Нужна регистрация, вход, JWT-токены, роли (admin/member), проверка
владения задачей.

**Решение.** JWT (HS256) с PBKDF2/hashing через passlib[bcrypt]. Эндпоинты:
`POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `GET /api/v1/auth/me`,
`GET /api/v1/auth/users`. Создание/редактирование/удаление задач требуют
аутентификации; membres могут править только свои задачи, админ — любые.

**Почему не OAuth2/OpenID Connect.** Демо-масштаб не оправдывает сложность
стороннего провайдера аутентификации. JWT с базовым хэшированием паролей
достаточно для демонстрации понимания принципов auth.

### ADR-006. Лента активности (activity feed)

**Контекст.** Нужно отслеживать, кто, что и когда сделал с задачами.

**Решение.** Отдельная таблица `activity` со связями к `tasks` и `users`.
Записывается при создании, обновлении и удалении задач. Эндпоинт
`GET /api/v1/activity` возвращает последние события с именем актёра.

### ADR-007. ИИ-аудит как отдельный сервис

**Контекст.** Требование: «проводить аудит наработок ИИ-агента и формировать план
рефакторинга».

**Решение.** `AuditService` выполняет реальные проверки, а не возвращает
заглушку:

1. сверяет `sqlite_master`/`pg_indexes` с каталогом обязательных индексов;
2. ищет таблицы без индексов (риск full scan);
3. ищет задачи без исполнителя, «зависшие» в `in_progress`, заблокированные
   критические задачи;
4. считает оценку качества (штрафы за critical/warning/info);
5. формирует план рефакторинга с приоритетом и оценкой трудоёмкости (S/M/L).

**Почему статический анализ, а не LLM.** Проверки должны быть детерминированными и
воспроизводимыми: одинаковый вход — одинаковый отчёт. LLM-шаг добавляется
поверх как необязательное обогащение.

### ADR-008. Структурное логирование и трассировка запросов

Каждый запрос получает `x-request-id` (генерируется, если не пришёл), который
возвращается в ответе и пишется в лог. Логи — JSON, уровни `debug/info/warn/error`.
Это связывает логи, метрики и ошибки в одну цепочку.

### ADR-009. Frontend — React + TypeScript + Vite на Cloudflare Pages

Фронтенд — SPA на React 18 + TypeScript, собран через Vite. Страницы:
дашборд с KPI и SVG-графиком создания/выполнения задач, задачи с фильтрами,
поиском, пагинацией и live-синхронизацией (SSE + ETag/304, ADR-014), лента
активности, аудит ИИ, пользователи, вход/регистрация. 9 unit-тестов (React
Testing Library + Vitest); воркер покрыт 24 unit + 24 integration-тестами
(Miniflare: D1 + KV in-memory).

**Причины React.** Компонентный подход, простое управление состоянием, легкость
тестирования. Для démo не требуется Next.js — suffisamment статического хостинга
на Pages.

**Регистрация — toggle на экране входа, а не отдельный маршрут.** Pages отдаёт
статику без SPA-rewrites: хэш-роутинг `/login` привёл бы к 404 при прямом заходе
и обновлении. Один экран с переключателем режима — дешевле и надёжнее.

### ADR-010. Персистентность метрик на Workers: сброс дельт из того же изолята

**Проблема.** Изоляты Cloudflare Workers короткоживущие. Счётчики, накопленные
в памяти при обработке запросов, умирают вместе с изолятом, и `/metrics`
отдаёт пустоту. Первый вариант решения — сбрасывать счётчики по cron-триггеру —
оказался нерабочим: cron исполняется в **другом** изоляте и не видит счётчики
изолиата, обслужившего запросы.

**Решение.** Дельты счётчиков сливаются в D1 (`INSERT ... ON CONFLICT DO UPDATE
SET value = value + excluded.value`) из того же изолята, который обработал запрос,
и делается это в фоне через `executionCtx.waitUntil` — клиент не ждёт записи.
Запись троттлится: не чаще раза в секунду на изолят. При ошибке записи дельты
возвращаются в регистр, чтобы не потерять данные.

**Чем платим.** Одна запись в D1 на интервал (секунда) на изолят. Для продакшена
на этом масштабе правильнее Durable Object (сильносогласованный счётчик) или
Analytics Engine — оба варианта описаны как варианты развития.

**Итог.** `/metrics` отдаёт сумму персистентных счётчиков из D1 и текущих
гистограмм изолята. Prometheus видит накопленную историю запросов, ошибок,
попаданий в кэш — то есть данные, на которых строятся SLO-алерты из
`infra/prometheus/rules/slo.yml`.

### ADR-011. Секреты — только через `wrangler secret`

**Контекст.** Первоначально `JWT_SECRET` лежал plaintext в `wrangler.toml`
(`[vars]`) и попал в git. Любой, кто видел репозиторий, мог подписывать токены.

**Решение.** Секрет вынесен из `[vars]` и установлен через
`wrangler secret put JWT_SECRET` — Cloudflare хранит его зашифрованным, не
показывает в dashboard/API в plaintext, не попадает в деплоймент-бандл. В
`[vars]` осталось только несекретное: `ENVIRONMENT`, `LOG_LEVEL`,
`FRONTEND_ORIGIN` (ADR-012).

**Ротация.** Повторный `secret put` инвалидирует все выданные токены —
демо-аккаунты просто перелогиниваются. В CI деплой должен уметь `secret put`
(токен Cloudflare с правами Workers Secrets).

### ADR-012. CORS — явный allowlist вместо `origin: *`

**Контекст.** `origin: "*"` на stateful API (JWT-сессии, записи в БД) позволял
любому сайту читать ответы авторизованных запросов из браузера жертвы.

**Решение.** Ручной middleware (`worker/src/middleware/index.ts`): только
origin'ы из `FRONTEND_ORIGIN` (comma-separated) получают
`Access-Control-Allow-Origin` + `Vary: Origin`. Preflight отвечается 204 с
заголовками. Запросы без `Origin` (server-to-server) пропускаются без ACAO.

**Найденный дефект.** `c.header()` в Hono не применяется к `Response`,
возвращённому напрямую из обработчика — preflight терял ACAO. Исправлено
построением `Response` с заголовками в конструкторе; покрыто интеграционным
тестом (allow/deny origin).

**Компромисс.** Новый origin = переменная + редеплой. Для продакшена с
динамическими клиентами — Cloudflare Access или конфиг в D1.

### ADR-013. Rate limiting — token bucket в KV, fail-open

**Контекст.** Публичный API с `/login` — цель brute-force и абьюза.

**Решение.** Token bucket в KV (`worker/src/lib/rateLimiter.ts`), классы
маршрутов: `auth` 10/мин, `write` 60/мин, `read` 120/мин на IP
(`cf-connecting-ip`). Заголовки `X-RateLimit-Limit/Remaining/Class`, 429 с
`Retry-After`. Классификация — `classifyRequest()` по методу и пути.

**Компромисс (fail-open).** При деградации KV лимитер пропускает запросы:
доступность API важнее строгости квоты (см. ADR-015). KV eventually consistent —
счётчик может дрейфовать при параллельных запросах; для точности — Durable
Object.

### ADR-014. Синхронизация UI: версия в D1 + ETag/304 + SSE

**Контекст.** Изоляты Workers короткоживущие и независимы: SSE-подключение и
мутация задачи почти наверняка исполняются в разных изолятах. Единственный
источник истины — D1 (строгая консистентность в регионе).

**Решение.** Три уровня:
1. Мутации инкрементируют `sync_state.tasks_version` (D1) в той же транзакции,
   что и запись задачи.
2. Клиент слушает публичный SSE `/api/v1/sync/tasks/stream` — стримит **только
   номер версии** (без данных задач), поэтому не требует авторизации:
   EventSource не умеет заголовки, а утечка счётчика версий — некритична.
3. При изменении версии — условный GET `/api/v1/tasks` с `If-None-Match`
   (ETag = `W/"{version}-{hashQuery}"`): 304 = локальная копия актуальна, ноль
   трафика и рендера. При обрыве SSE — fallback-опрос `/sync/version` раз в 3 с.

**Компромисс.** SSE-стрим полирует D1 раз в 1.5 с на соединение — осознанный
выбор для демо-маштаба (десятки зрителей). При росте нагрузки правильный путь —
Durable Object, держащий подключения и получающий версию из очереди; путь
миграции описан в `worker/src/routes/sync.ts`.

### ADR-015. Отказоустойчивость: circuit breaker KV + best-effort очередь

**Контекст.** KV и Queues — управляемые сервисы; их деградация не должна
ломать основной поток (чтение/мутация задач).

**Решение.**
- Circuit breaker для KV (`worker/src/lib/kvCircuit.ts`): 5 ошибок → open на
  30 с → half-open probe. Reads → cache miss (промах в D1), writes → no-op.
  `/health` показывает `cache: "degraded"`; метрики `kv_errors_total`,
  `kv_circuit_open`. Все операции кэша — через breaker (`lib/cache.ts`).
- Мутации задач больше не падают при ошибке `queue.send`: enqueue обёрнут в
  best-effort try/catch (`queue_send_errors_total`), consumer догонит при
  следующей версии — аудит и переиндексация идемпотентны.

**Компромисс.** При открытом breaker кэш отключён (все чтения — в D1);
потерянные редкие jobs `audit.run` восполняются ручным запуском.

## 4. Производительность

- пагинация на стороне БД (`LIMIT/OFFSET`), ограничение `pageSize <= 100`;
- агрегаты считаются в БД, не в Python;
- «горячие» выборки кэшируются, запись инвалидирует кэш;
- индексы под фильтры и сортировку;
- гистограмма латентности позволяет отслеживать p95/p99.

## 5. Надёжность

- `startupProbe` / `livenessProbe` / `readinessProbe` в Kubernetes;
- `terminationGracePeriodSeconds: 30` + `preStop sleep` для корректного завершения;
- HPA по CPU и памяти (2…10 реплик);
- PodDisruptionBudget `minAvailable: 1`;
- rolling update с `maxUnavailable: 0`;
- ограничения ресурсов и `readOnlyRootFilesystem`, `drop: [ALL]`;
- повторяемые задачи очередей с backoff и DLQ.

## 6. Что осознанно не сделано

- версионирование API (контракт зафиксирован, но не версионирован);
- интеграция с NiFi — в вакансии она упомянута, но в демо нет внешнего
  data-flow, к которому её можно было бы подключить;
- Airflow — упомянут в вакансии, но для этого демо Celery достаточно;
- OpenAPI/Swagger документация — `/docs` доступен в FastAPI, но не заполнен
  примерами.
